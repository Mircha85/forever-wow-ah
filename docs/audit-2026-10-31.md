# Project Audit — 2026-10-31

**Scope:** full read-through of the working tree at `7a9fdf1` (Vercel Hobby
migration merge) plus the uncommitted hardening pass.
**Method:** static analysis only. `npm run typecheck`, `npm run lint` and
`npm test` were **not** executed — see [Verification status](#verification-status).
**Inputs:** `docs/wow-ah-live-retail-mode.md` (live retail design),
`docs/superpowers/plans/2026-10-14-vercel-hobby-migration.md` (migration plan),
`extraction-direct-summary.json` (last real extraction measurement).

---

## Executive summary

The architecture is sound: product/region/realm-partitioned R2 layout, a
bearer-gated write path, a client-side binary decoder that keeps JSON off the
hot path, and a rate limiter with a deliberately narrow signature.

The uncommitted hardening pass moves in the right direction — it closes a
real quota-abuse hole on `/api/items-meta` and a real DoS hole on the
per-item blob route. **But it was applied to half the surface and it traded
an availability bug for an honesty bug.** Four findings are blocking:

1. **F0** — every price history, every 24 h delta and every hourly heat map
   the dashboard renders is **fabricated**, on the happy path as well as on a
   cache miss. The synthetic-data problem is much wider than the hardening
   pass exposed.
2. **F1** — the per-item blob route serves **synthetic prices as if they were
   real market data**, and persists them to R2.
3. **F2** — the `state.bin` route **still rebuilds the entire realm snapshot on
   a cache miss** — the exact vector the hardening removed from the per-item
   route.
4. **F3** — the extraction pipeline as scheduled would cost **at least
   ~$1,425/month in R2 requests** (and up to ~$17.8k/month), against a stated
   target of `$0/month`.

On top of those, the game namespace (`retail` vs `forever`) is resolved
inconsistently in three different places, and the metadata cache that the new
cache-only route depends on has no durable backing — so on Vercel it is cold
almost every time.

## What the P0 remediation changed

One write-path change fixed all five P0 findings at once, because they were
one problem wearing five hats.

**Before:** every ingestion run wrote one R2 object *per item* — about
15 700 per realm, 175 realms, every 30 minutes — and every item's price
history was invented by a seeded pseudo-random walk. Reading an item
rebuilt the whole realm from Battle.net on a miss, or fabricated a blob
and wrote it to R2.

**After:** an ingestion run writes **three objects per realm**:

| Object | Contents | Measured size (15.7 k items) |
|---|---|---|
| `state.bin` | the item summary table the dashboard lists | 440 KB |
| `realm.bin` | every item's aggregate and its auction lots | 2.1 MB gzipped |
| `history.bin` | the rolling store of observed values, gzipped | 1.38 MB gzipped |

The per-item view is now *derived* at read time from those two archives
and served in exactly the same `UNDR v1` binary format the browser has
always decoded — the client is unchanged.

### The operating point, measured

Measured by running the real ingestion path over a **synthetic snapshot
with the same shape as realm 1305** — 15 708 items (the real item count
from the last extraction) and 177 418 auctions with a heavy-tailed lot
distribution — in a fresh process. It is a workload simulation, not a
capture of live Battle.net data; the durations and archive sizes are
properties of the code and of the workload's shape:

| | Before | After |
|---|---|---|
| One realm's ingestion | 195.7 s | **0.66 s** |
| R2 objects written per realm | 15 708 + 1 | **3** |
| R2 requests per month (175 realms, 30 min) | ~3.96 billion | **~25 000** |
| Bytes moved per run (write + read) | ~94 MB | **~5.7 MB** |
| Traffic per month | ~790 GB | **~48 GB** |
| Cost per month | ~$17 800 | **$0** (inside R2's free tier) |
| Dashboard item click | — | 91 ms cold, 0 ms warm |

The extraction fits Vercel Hobby's 120-second budget with a factor of 180
to spare, and the fleet's traffic sits at roughly half the platform's
100 GB allowance — before counting that R2's own request allowance is not
exhausted either.

The numbers that made this possible were not guesses. They came from
running the ingestion path over a snapshot of the right shape, which is
also how F15 was found: the first version of the fix wrote a 7.4 MB
history per run because an item that stays listed accrues an observation
every hour. The budget that bounds it was added after measuring, not
before.

What has **not** been measured against live data: the Battle.net
round-trip, the R2 request latency and the real archive sizes in the
bucket. Those need the credentials and a real run.

- **Honesty:** no number the dashboard shows is invented. The price series
  contains only observations a run actually made; the 24 h delta compares
  two real observations about a day apart; and when there is no second
  observation yet, the delta renders as "not measured yet" rather than a
  number.
- **Read path:** both blob routes are pure reads. No upstream call, no
  write, no fabricated fallback. A miss is a 404 that says what is
  missing.

### What the operator will see after deploying

- **Run `POST /api/pipeline/run` once, right after the deploy.** Until a
  run has happened, the realm has no `realm.bin`, so every item detail
  view answers 404 — the item *table* still works, because `state.bin`
  keeps its format and is still in R2.
- Between the deploy and that first run, `state.bin` is still the old
  file, so its 24 h deltas are the ones the old code invented. They are
  replaced by "not measured" as soon as the first new run writes it.
- The first ingestion run finds no history, so **every 24 h delta is
  "not measured yet"** and the "24 h Market Movers" strip stays empty.
- Deltas start appearing **24 hours after the first run**, as the
  baseline reaches back a day. The price series fills in from the first
  run; the daily chart reaches 14 points after 14 days, the hourly heat
  map after 7.
- The ~2.6 GB of orphaned per-item blobs already in R2 are no longer
  written but are still stored. Deleting them is a separate, explicitly
  approved operation.

### F0 — Every price history, delta and heat map is fabricated (P0)

*Discovered 2026-10-31 while planning the F1/F2/F3 remediation. It is the
same class of defect as F1, but on the happy path, and it is the reason F1
cannot be fixed by patching one route.*

**Where:** `src/services/aggregator.ts:244` — `generateHistoricalContext`

For **every** item, on **every** run, the aggregator invents:

- 14 days of `dailyHistory` points (timestamp, min, median, mean, quantity,
  auction count) — a seeded pseudo-random walk around the current price
- 168 `hourlyDeltas` points (timestamp, min, median, quantity) — a random walk
  with a diurnal activity factor and invented "dead hours"
- `priceDelta24h` and `quantityDelta24h` — **computed from that invented
  history**, not from any real prior observation

Those invented values are written into `state.bin` (which is what the item
table and the "top movers" ranking read) **and** into every per-item blob
(which is what the charts, the heat map and the item modal read).

So even after F1 and F2 are fixed — after the pipeline ingests a genuinely
live snapshot and the cache-miss lie is gone — the dashboard would still
show a fabricated 24 h price delta, a fabricated 14-day price chart and a
fabricated hourly activity heat map, presented with the same confidence as
the real quantities next to them.

**Impact:** the delta column and both charts are the features the dashboard
is built around, and none of their values are observed. A user making a
flipping decision on a "+18.4% overnight" reading is reading a random number
seeded by the item id.

**Recommended fix:** capture real history from successive snapshots — store a
per-realm rolling history artifact and derive the 24 h delta from two
genuinely separate observations. Until enough observations exist, the delta
and the charts must show an explicit "not enough data yet" state rather than
an invented series. This necessarily changes the write path, which is the
same change F3 needs, so the two should be solved together.

### F1 — Synthetic item data is served and persisted as real market data (P0)

**Where:** `app/api/data/cached/[product]/[region]/[realmId]/[hash]/[file]/route.ts:77-85`
→ `src/services/aggregator.ts:365` (`generateSingleItemBin`)

The cache-miss policy added in the uncommitted diff routes a miss straight to
`generateSingleItemBin`. That function fabricates a fixed set of numbers:

- `minPrice = 1800` copper, `medianPrice = 2200`, `meanPrice = 2100`
- `totalQty = 120`
- 5–25 synthetic auction lots with deterministic ids (`100000 + itemId * 10 + i`)
- a synthetic 24 h history and hourly delta series

It then **writes the fabricated blob to R2** (`aggregator.ts:419`), so it is
not merely returned once — it becomes a cached "real" artifact served to every
subsequent reader until the next pipeline run overwrites the key.

The dashboard fetches exactly this route when a user opens an item's detail
view / binary inspector (`app/page.tsx:313`), so the fabricated prices render
in the UI with no marker distinguishing them from live auction data.

This contradicts the stated design principle in
`docs/wow-ah-live-retail-mode.md:18`:

> A healthy-looking dashboard of fake numbers is a worse failure mode than a
> loud one.

**Impact:** users see plausible, well-formed market data that does not exist.
The failure is silent and survives in the cache.

**Recommended fix:** answer **404** on a per-item cache miss (the blob is not
ingested yet — a loud, correct "no data" state), and stop writing fabricated
blobs to R2. If a demo mode is still wanted, gate it behind an explicit
env flag and label the payload (`X-WoW-AH-Source: synthetic`) rather than
letting it share the `retail/` prefix.

### F2 — The `state.bin` route still rebuilds the whole snapshot on a cache miss (P0)

**Where:** `app/api/data/cached/[product]/[region]/[realmId]/state.bin/route.ts:54-68`

The hardening removed the snapshot rebuild from the per-item route but left it
in the `state.bin` route, which is the route with the highest blast radius:

```ts
if (!buffer) {
  const blizzard = new BlizzardService({ region, namespace: ... });
  const { snapshot } = await blizzard.fetchAuctionSnapshot(connectedRealmId, true);
  await AuctionAggregator.processSnapshot(product, region, connectedRealmId, snapshot, r2);
  buffer = await r2.getBin(stateKey);
}
```

Per miss this burns one Battle.net snapshot (10–25 MB of JSON), rewrites
`state.bin` **and every per-item blob for the realm** (~15.7 k PUTs, see F3),
and holds the whole snapshot in memory. The rate limit is 30 req/min per
client IP, and the client identity is IP-based — so 30 distinct realm ids per
minute is enough to force 30 full snapshot rebuilds.

**Impact:** the DoS/quota vector the hardening set out to close is still open
on the sibling route. The two routes now behave differently for the same
class of event (cache miss), which is also a correctness inconsistency.

**Recommended fix:** apply the same policy — on a cache miss, return **404**
and let the bearer-gated pipeline populate the blob. If a live rebuild is
wanted for UX, it must happen behind the bearer gate, not in a public GET.

### F3 — The scheduled cadence implies ~$17.8k/month of R2 PUT requests (P0)

**Where:** `src/services/aggregator.ts:166` + `uploadItemsParallel`
(`aggregator.ts:435`), `src/services/r2.ts:240` (`getBinMetadata`),
`realm-ids.json` (175 realms), `scripts/seed-cron-jobs.ts` (`*/30 * * * *`)

Measured inputs from the last real extraction (`extraction-direct-summary.json`):
**15 708 unique items** for one EU realm.

The per-item write path does **two R2 operations per queued item per run**:

1. a `HeadObject` via `getBinMetadata` — to decide whether to skip the write;
2. a `PUT` — only if the stored byte length differs.

`getBinMetadata` is served from `R2Service.localMemoryCache` when present
(`r2.ts:241`), but that cache lives inside the serverless instance, so on a
cold instance every one of those HEADs is a real request to R2.

The cost therefore splits into a **certain** part and a **conditional** part.
R2's free tier is 10 GB storage, **1 M Class A (writes)** and **10 M Class B
(reads/HEAD)** per month, so both numbers are net of that allowance:

| Quantity | Value |
|---|---|
| Realm-runs per month (175 realms × 48/day × 30) | 252 000 |
| Queued items per realm per run | ≤ 15 708 (only items with ≥ 3 auctions are queued, `aggregator.ts:74`) |
| **HEADs per month** | **~3.96 billion** |
| R2 Class B (reads/HEAD) | $0.36 / million, 10 M free |
| **Certain monthly cost** | **~$1 420** |
| PUTs per month (only when the byte size changed) | 0 … ~3.96 billion |
| R2 Class A (writes) | $4.50 / million, 1 M free |
| **Worst-case monthly cost** | **~$19 200** |

Storage is irrelevant here — the same keys are overwritten every run, so the
cost is entirely in operation count. (Storage for ~5.5 GB of blobs would be
~$0.08/month.)

This directly contradicts the migration plan's hard constraint
(`docs/superpowers/plans/2026-10-14-vercel-hobby-migration.md:15`):

> Target total recurring spend: **$0 / month**.

The same table with a cheaper write shape — and note that the free tier is
what makes the "$0/month" target reachable at all:

| Strategy | Class A / month | Class B / month | Monthly cost |
|---|---|---|---|
| Per-item blobs, current shape | 252 K + up to ~3.96 B | up to ~3.96 B | ~$1 420 (floor) … ~$19 200 |
| **`state.bin` only** | ~252 K | ~252 K | **$0.00** — both under the free tier |

`state.bin` already carries per-item `minPrice / medianPrice / meanPrice /
quantity / auctionCount / 24h deltas` at 28 bytes per item
(`README.md`, "Binary format — UNDR v1"), i.e. ~440 KB for a 15.7 k-item
realm. The per-item `.bin` files only add the 24 h history, hourly deltas and
active lots — the payload the binary inspector shows.

#### F3b — the size-match skip preserves stale prices (P0, found in the same mechanism)

`uploadItemsParallel` skips the PUT when the stored size matches
(`aggregator.ts:448`), justified in its comment by:

> The encoder is deterministic for identical input snapshots, so a size match
> is a strong signal the content also matches.

That reasoning does not hold. The snapshot is never identical — it is a fresh
fetch, and the encoder stamps `lastUpdated: generatedAt` into the blob
header (`aggregator.ts:152`). More importantly the *prices* change on every
auction cycle while the *size* usually does not: the encoded item blob is a
fixed header + 14 daily points + 168 hourly points + `28 × min(80, lotCount)`
bytes of lots, so the length depends only on the number of active lots.

The practical result: **for every item whose lot count did not change, the
blob in R2 keeps the prices from whenever the size last changed** — which can
be days old. The pipeline's own `state.bin` is rewritten every run and shows
current prices, so the item table and the item detail modal can disagree
about the same item at the same time. Only the binary inspector surfaces the
staleness (`lastUpdated` is decoded at `binDecoder.ts:155` and rendered at
`BinaryInspectorModal.tsx:184`); the item modal does not.

**Recommended fix:** never use byte length as a freshness signal. Either
always write, or compare a content hash / ETag against the previous run's
value stored alongside the blob. Combined with the F3 write-shape change, the
cheapest correct answer is to stop writing per-item blobs on the schedule
altogether (see the F1/F2/F3 remediation) and derive the per-item view from
canonical per-realm data at read time.

**Recommended fix (pick one):**
1. **Drop the per-item blob writes** and derive the inspector payload from
   `state.bin` plus a small number of on-demand live fetches. Biggest saving
   by an order of magnitude, no functional loss for the table view.
2. **Reduce the sweep set** — track a handful of realms at 30 min and the rest
   hourly or daily.
3. **Reduce cadence** — 30 min → 6 h cuts the cost ~12×.

Whichever is chosen, the plan's `$0/month` constraint needs re-stating in
terms that survive arithmetic.

### F4 — Namespace and product are resolved differently in three places (P1)

**Where:**
- `src/services/blizzard.ts:117-120` — default namespace is **forever**
- `app/api/pipeline/run/route.ts:93-94` — `BLIZZARD_PRODUCT` picks the **R2 prefix** only
- `app/api/data/cached/.../state.bin/route.ts:57` — namespace from the **URL `product` param**
- `scripts/extract-direct.ts:184` — namespace hardcoded to **retail**

`BLIZZARD_PRODUCT` never influences the namespace. The four paths in play:

| Path | Blizzard namespace | R2 prefix written |
|---|---|---|
| `POST /api/pipeline/run` (cron, every 30 min) | `dynamic-classicann-{region}` (forever) | `retail/` |
| `scripts/extract-direct.ts` (manual) | `dynamic-{region}` (retail) | `retail/` |
| `GET .../state.bin` cache miss | from URL param (`dynamic-{region}` for retail) | `retail/` |
| `POST /api/items-meta/warm` | `dynamic-classicann-{region}` (forever) | n/a |

Two of these write the **same R2 prefix with data from different games**, and
whichever ran last wins. The cron path and the manual path therefore fight
over the same keys.

There is also a schedule problem: `blizzard.ts:113-120` defaults to the
Forever namespace, while `docs/wow-ah-live-retail-mode.md:18` and
`scripts/extract-direct.ts:72` both say **retail until 2026-11-04** — the
Forever API goes live on that date. `blizzard.ts` also notes that the previous
Retail default would "succeed against the wrong game rather than failing",
which is a valid argument for making the product explicit rather than
defaulting to either.

Finally, neither `BLIZZARD_PRODUCT` nor `BLIZZARD_NAMESPACE` is documented in
`.env.example`, although the code reads both.

**Impact:** the dashboard's `retail/` tree can contain Forever data or Retail
data depending on which job ran last; the label on the data is not reliable.

**Recommended fix:** make the product a single source of truth that drives
**both** the namespace and the R2 prefix — e.g. `BLIZZARD_PRODUCT=retail|forever`
resolved once in `BlizzardService`, with the prefix derived from the same
value. Reject a mismatched `product` URL param rather than silently using it
to pick a namespace. Document both variables in `.env.example`, and set the
default to the game that is actually live.

### F5 — The metadata cache has no durable backing (P1)

**Where:** `src/services/itemMetadataCache.ts:10-12`, `app/api/items-meta/route.ts`

The new public route reads exclusively from an in-memory `Map` parked on
`globalThis`. On Vercel that map lives inside one serverless instance and is
destroyed on recycle, so the cache is cold for a large share of requests.

Phase 4 of the live-retail design called for a durable tier —
`src/services/itemMetadataPersistence.ts`, writing
`data/items-meta/{region}/{itemId}.json` to R2 — and it was never implemented
(the file does not exist). The two-tier design ("hot" in-memory + "durable"
in R2) is therefore hot-only.

This matters more after the hardening than before it. The old route warmed on
demand, so a cold cache still produced real metadata for the requested ids
(paid for in Battle.net quota). The new route is cache-only, so a cold cache
returns **nothing** and the dashboard falls back to "Unknown Item #X" — the
same rendering it already uses for items missing from the hardcoded catalog.

The inline warming added to `POST /api/pipeline/run`
(`app/api/pipeline/run/route.ts:104-126`) only warms the instance that
executed the pipeline; the dashboard request usually lands on a different
one.

**Impact:** in production, most rows show unknown-item placeholders. The
metadata feature is effectively inert on the target platform.

**Recommended fix:** implement the R2 persistence tier from the design doc —
write each warmed item's metadata to `data/items-meta/{region}/{itemId}.json`
and read through to it on a cache miss. Read-through from R2 is cheap (a
`GET` per id, ~$0.36/million Class B) versus the current per-item PUT
problem in F3.

### F6 — Single-realm extraction exceeds the Vercel Hobby function limit (P1)

**Where:** `extraction-direct-summary.json`, `docs/superpowers/plans/2026-10-14-vercel-hobby-migration.md:288`

The last measured extraction took **195.7 s** for a single EU realm
(15 708 items), against Vercel Hobby's **120 s** maximum function duration.
The plan flagged this exact risk at Task 5 Step 4:

> if extraction of a single realm exceeds that, the plan must switch to Pro
> ($20/mo) or chunk by item-id range

The measurement was taken locally, so it is a proxy rather than a Vercel
number — but it is the best available and it is already 1.6× the limit. The
per-item blob writes identified in F3 are the most likely dominant cost and
would shrink substantially if F3 is fixed.

**Recommended fix:** fix F3 first (it shrinks the write path), then re-measure
on Vercel. If still over budget, chunk the aggregation by item-id range and
accept several invocations per realm per cycle.

### F8 — The dashboard hydrates metadata once per realm, then never again (P2)

**Where:** `app/page.tsx:101` (`hydratedForRealmRef`)

hydrated for. A cache that warms *after* the page loaded is never picked up
without a manual reload, and switching away and back to a realm does not
re-hydrate it.

**Recommended fix:** re-hydrate when the returned payload reports metadata
that the local map is missing, or when the cache-size signal changes.

### F11 — Dead route with a stale R2 prefix (P2)

**Where:** `app/api/realms/[region]/[connectedRealmId]/items/route.ts:47`

The route enumerates per-item blobs under:

```
data/cached/${region}/${connectedRealmId}/
```

Every other route in the app uses the product-partitioned layout
`data/cached/{product}/{region}/{realmId}/…` (see `R2Service.generateItemKey`
and `generateStateKey`). The prefix this route lists therefore no longer
exists, so it always answers with an empty list.

Nothing in `app/` or `src/` calls it — it is dead code left over from the
layout migration in `14b07fb`. It also takes no `product` parameter, so it
cannot be pointed at the right prefix without a change.

It is also the wrong shape for the current data volume: it lists every shard
directory of a realm and then lists every key inside each one, which for a
15.7 k-item realm is 256 directory listings plus ~16 pages of keys — 272
LIST calls per invocation of a route that has no caller.

**Recommended fix:** delete it, or bring it onto the product-partitioned
layout and give it a caller. If the per-item blob layout goes away as part of
the F3 remediation, deleting it is the cleaner option.

### F12 — The cross-realm comparison generated its prices from a hash (P0, fixed)

**Where:** `src/components/MultiRealmPriceTable.tsx:98-104` (now unused)

The item modal rendered a "Cross-Realm Price & Stock Comparison" table. For
every realm other than the current one it computed a price from a hash of
the item id and the realm id:

```ts
const hash = ((itemId * 2654435761 + realm.id * 805306457) >>> 0) % 1000;
const variation = 0.85 + (hash / 1000) * 0.4; // +/- 20%
```

The result was a number shaped like a price, next to the realm's real
name, in a table titled "Cross-Realm Price & Stock Comparison". Nothing
in the UI marked it as a placeholder. It was the same class of defect as
F0 and F1, on the happy path, and it survived both remediations because
nobody had looked at that component.

**Fix:** the table was removed from the item modal and replaced with a
realm switcher that loads the *real* item view from another realm —
straight from that realm's archive, so every number it shows is measured.
The component file itself is now unreferenced; deleting it is left to the
operator (the file removal needs an explicit approval).

### F13 — The public realm listing called Battle.net once per realm (P1, fixed)

**Where:** `app/api/realms/route.ts` (before the fix)

The route listed the realms in R2 and then resolved each realm's display
name by calling `blizzard.fetchConnectedRealmName(id)`. On a cold instance
that is **175 upstream calls per public request** — a request anyone can
make, against a shared API key, 60 times a minute per client.

**Fix:** the upstream call moved to the bearer-gated ingestion path, which
resolves a realm's name once and writes it to
`data/cached/{product}/{region}/names.json`. The public route reads that
file. The listing is also cached for a minute per region, which bounds the
per-realm HEAD requests as well.

### F14 — `uploadBin` reported success when the write had failed (P1, fixed)

**Where:** `src/services/r2.ts` (before the fix)

A failed R2 write was logged, the blob was kept in the process cache, and
the call returned `success: true`. An ingestion run would then report that
it had stored a snapshot that existed only in memory and would die with
the instance.

**Fix:** the upload reports `success: false` with the reason, and the
aggregator fails the run when any of its three writes did not land.

### F15 — The history archive grew without bound (P1, fixed)

Measured on a snapshot of realm 1305's shape (15 708 items): an item that
stays listed accrues one observation an hour, so the hourly series
reaches 2.6 million points and the archive is **7.4 MB compressed**. The
archive is rewritten *and* read back on every run, so at 175 realms on a
30-minute schedule that is ~145 GB a month of traffic — past Vercel
Hobby's 100 GB allowance.

**Fix:** the history has a byte budget. When the archive would exceed it,
the hourly series is trimmed first — keeping each item's 24-hour anchor,
which is what the price delta is computed from — and the daily series
only if that is not enough. Measured after the fix: **1.38 MB**, and the
delta stays measurable for every item.

### F16 — An empty, older or partial snapshot overwrote a good one (P1, fixed)

The pipeline wrote whatever it was handed. An upstream hiccup that
returned a truncated snapshot would replace a good one with a near-empty
one, and the dashboard would show a realm that had "lost" most of its
listings.

**Fix:** the run is refused when the snapshot has no auctions, when it is
older than the stored one, or when it holds fewer than a quarter of the
stored item count. The stored snapshot is left untouched.

## Recommended order of work

The four P0s are one problem, not four. F0 forces the write path to change
(real history has to be captured from somewhere), and F3 forces the write
path to change anyway (the current one cannot afford to run 175 realms every
30 minutes). Fixing F1 and F2 in isolation — patching the cache-miss branch
and leaving the rest of the pipeline alone — would close the visible symptom
and leave both the fabricated history and the bill exactly where they are.

**Phase 1 — one write-path change (F0, F1, F2, F3, F3b, and F6 as a
side effect)**

1. **F3 / F3b** — decide and implement the write shape: stop writing 15 708
   per-item blobs per run, and never use byte length as a freshness signal.
2. **F0** — capture real history from successive snapshots and derive the
   24 h delta and the charts from it. Until two real observations exist, the
   delta and the charts must render an explicit "not enough data yet" state.
3. **F1 / F2** — with the write path fixed, the public GET routes become
   pure reads: no upstream call, no write, no fabricated fallback. A miss is
   a 404 with a message, not a synthetic blob.
4. **F6** — re-measure the extraction duration once the write path is
   smaller; it should fall well inside the 120 s Hobby budget.

**Phase 2 — the rest**

5. **F4** — one product resolver driving both namespace and R2 prefix; document the env vars.
6. **F5** — implement the R2 metadata persistence tier from design phase 4.
7. **F7 / F8** — align the warm cap with the hydration target; allow re-hydration.
8. **F9 / F10** — refresh the README, retire the stale TODOs, decide the fate of
   `Dockerfile` / `run-server.mjs` / the gitignored doc paths.
9. **F3 follow-up** — set `BLIZZARD_PRODUCT` to whichever game is live on
   2026-11-04, and verify the cron pipeline end to end against it.
